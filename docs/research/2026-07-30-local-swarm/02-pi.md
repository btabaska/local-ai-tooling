## 0. TL;DR for this rig

- pi's **core deliberately ships without subagents, MCP, plan mode, or LSP**. All four exist as **third-party extensions**, and the extension API is powerful enough that they are real implementations, not toys.
- pi has **first-class local-model support**: built-in `llama.cpp` provider, `/llama` model management with HF downloads (0.81.0), and a LiteLLM provider extension.
- pi's **0.82.0 "constrained tool sampling"** is the single most relevant recent feature for this rig — it lets tools *require* strict JSON-Schema-constrained sampling, which is the standard fix for flaky local-model tool calls.
- For swarm hosting, pi's **RPC mode + SDK + `@tintinweb/pi-subagents`** is a stronger foundation than opencode. See §11 and §13.

## 2. Architecture — TUI, library, and headless

pi is **all of the above**. Four operating modes (source: README + `docs/rpc.md`, `docs/json.md`, `docs/sdk.md`):

| Mode | Invocation | Use |
|---|---|---|
| **Interactive TUI** | `pi` | Normal human use |
| **Print / one-shot** | `pi -p "prompt"` | Scripting, single turn |
| **JSON event stream** | `pi --mode json "prompt"` | Line-delimited JSON events to stdout for custom UIs |
| **RPC** | `pi --mode rpc` | Bidirectional JSONL over stdin/stdout — **process integration, cross-language** |
| **SDK** | `import` from `@earendil-works/pi-coding-agent` | Embed in your own TypeScript app |

**Package exports** (from npm metadata):
- default → `./dist/index.js` (types `./dist/index.d.ts`)
- `./rpc-entry` → `./dist/rpc-entry.js`
- bin: `pi` → `dist/cli.js`

**Monorepo packages** (<https://github.com/earendil-works/pi>):
- `@earendil-works/pi-ai` — unified multi-provider LLM API
- `@earendil-works/pi-agent-core` — agent runtime, tool calling, state
- `@earendil-works/pi-coding-agent` — the CLI/SDK
- `@earendil-works/pi-tui` — terminal UI library with differential rendering

### 2.1 SDK surface
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md>

- **`createAgentSession(options)`** — main entry point.
- **`AgentSession`** — manages "message history, model state, compaction, and event streaming". Core methods: **`prompt()`**, **`subscribe()`**.
- **`ModelRuntime`** — auth + model selection; resolves credentials from stored auth files, env vars, runtime overrides.
- **`ResourceLoader`** / **`DefaultResourceLoader`** — discovers extensions, skills, prompt templates, context files from `~/.pi/agent/` and project `.pi/`.
- **`SessionManager`** — in-memory or file-backed sessions with tree-structured branching.
- **`defineTool()`** — custom tools.
- Events to subscribe: `message_update`, `tool_execution_start`, `agent_end`, etc.

Docs state the SDK is "preferred when you want type safety" and "direct access to agent state", whereas RPC suits "cross-language or process-isolated integrations."

### 2.2 RPC protocol
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md>

Strict JSONL, **LF-delimited only**. Docs explicitly warn: *"Split records on `\n` only"* — do **not** use Node's `readline`, which treats Unicode separators as newlines. Each command takes an optional `id` for correlation.

**Commands** (verified names):
- Prompting: `prompt`, `steer` (mid-run injection), `follow_up`, `abort`
- State: `get_state`, `get_messages`, `get_entries`, `get_tree`, `get_session_stats`
- Model: `set_model`, `cycle_model`, `get_available_models`, `set_thinking_level`
- Queues: `set_steering_mode`, `set_follow_up_mode` (`"all"` vs `"one-at-a-time"`)
- Compaction: `compact`, `set_auto_compaction`
- Shell: `bash` (streams via `bash_execution_update`)
- Sessions: `new_session`, `switch_session`, `fork`, `clone`, `export_html`
- Discovery: `get_commands`

**Events:** `agent_start`, `agent_end`, `agent_settled`, `turn_start`/`turn_end`, `message_start`/`message_update`/`message_end`, `tool_execution_start`/`update`/`end`, `queue_update`, `compaction_start`/`end`, `auto_retry_start`/`end`. `message_update` carries `text_delta`, `thinking_delta`, `toolcall_delta`.

**Extension UI over RPC:** extensions emit `extension_ui_request` on stdout, await `extension_ui_response` on stdin. Dialog methods (`select`, `confirm`, `input`, `editor`) expect responses; `notify`/`setStatus`/`setWidget`/`setTitle`/`set_editor_text` are fire-and-forget. In RPC mode `ctx.mode === "rpc"` and `ctx.hasUI === true`.

**This is the key swarm primitive.** `steer` + `abort` + `get_tree` + `fork` over a stable JSONL protocol means an external orchestrator can drive N pi processes and redirect them mid-flight.

### 2.3 Session format
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md>

- **Location:** `~/.pi/agent/sessions/--<path-with-slashes-replaced-by-dashes>--/<timestamp>_<uuid>.jsonl`
- **Format:** JSONL, one JSON object per line, each with a `type` field.
- **Tree model:** entries reference parents via `id` / `parentId`. Branching does **not** create new files. `buildContextEntries()` walks from current position to root, honoring compactions.
- **Entry types:** `SessionHeader`, `SessionMessageEntry`, `CompactionEntry`, `BranchSummaryEntry`, `ModelChangeEntry`, `ThinkingLevelChangeEntry`, `CustomEntry`, `CustomMessageEntry`, `LabelEntry`, `SessionInfoEntry`.
- Delete a session by deleting the `.jsonl`, or via `/resume` → `Ctrl+D`.

`CustomEntry` is how extensions persist state across restarts — important for building durable orchestration.

## 3. Agents / subagents

**Core pi has no subagents.** The README is explicit: *"Pi intentionally excludes certain features—like sub-agents, plan mode, and MCP—allowing developers to build these via extensions or install third-party packages."*

This is a design stance, not a gap in capability — the extension API is strong enough that community subagent implementations are full-featured.

### 3.1 `@tintinweb/pi-subagents` — the Claude-Code-equivalent
Source: <https://github.com/tintinweb/pi-subagents> · <https://www.npmjs.com/package/@tintinweb/pi-subagents>

```bash
pi install npm:@tintinweb/pi-subagents
```

- **Parallel execution**, default concurrency limit **4**, configurable queuing.
- **Background vs foreground:** background agents return immediately; foreground agents block.
- **Definition:** Markdown files in `.pi/agents/<name>.md` with YAML frontmatter.
- **Frontmatter fields:** `tools`, `extensions`, `disallowed_tools`, `model`, thinking level, system prompt, `isolated`, `isolation: worktree`, memory scope.
- **Built-in agent types:** `general-purpose` (inherits parent system prompt), `explore` (read-only), `plan` (no file modification).
- **Tools available to agents:** the 7 builtins (`read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`) plus extension tools.
- **MCP passthrough:** agents can request direct MCP tools in frontmatter with **`mcp:server-name`** syntax (requires an MCP extension installed).
- **Mid-run steering:** inject messages into a running agent to redirect it; stop agents (including background) via `/agents`.
- **Git isolation:** `isolation: worktree` runs the agent in a temporary repo copy.
- **Graceful limits:** agents get wrap-up warnings before hard termination.
- **Spawn interface:** an `Agent` tool with `type`, `prompt`, `model`, execution mode params.
- Notably, if `tools` is omitted the child gets pi's normal builtins (no `--tools` passed); if present it becomes an explicit allowlist; empty `tools` emits `--no-tools`. → implies pi's CLI *does* have `--tools` / `--no-tools` flags (the quickstart doc doesn't enumerate them; treat exact flag spelling as **likely** rather than verified).

## 4. Tools

### 4.1 Built-ins
Source: `docs/quickstart.md`, README

**Default four:** `read`, `write`, `edit`, `bash`.
**Additional read-only builtins available:** `grep`, `find`, `ls`.

That's it. No built-in web fetch, no built-in todo list, no built-in task/agent tool. (Community `pi-web-access`, `pi-search-hub`, `@pi-stef/web` fill the web gap.)

### 4.2 Custom tools
Written in **TypeScript**, registered from an extension. Verbatim from `docs/extensions.md`:

```typescript
pi.registerTool({
  name: "my_tool",
  description: "Does something useful",
  parameters: Type.Object({ action: Type.String() }),
  async execute(toolCallId, params, signal, onUpdate, ctx) {
    return {
      content: [{ type: "text", text: "Result" }],
      details: { data: "..." }
    };
  }
});
```

Schemas use **TypeBox** (`Type.Object(...)`) — confirmed by `typebox` being a dependency of pi-swarm and the doc examples.

- **Streaming:** `onUpdate` callback for incremental results.
- **Cancellation:** `signal` (AbortSignal).
- **Custom rendering:** `renderCall` / `renderResult` using `@earendil-works/pi-tui` components (Box, Text, Container); `renderShell: "self"` for full control.
- **Dynamic tool loading:** `pi.setActiveTools()` lets a "loader tool" activate additional tools at runtime. Native deferred loading works on **Anthropic 4.5+ and OpenAI gpt-5.4+** — i.e. **not** on local models; use the loader-tool pattern instead.
- **Output truncation is mandatory:** default 50KB / 2000 lines, via `truncateHead()` / `truncateTail()`.
- **Concurrency safety:** `withFileMutationQueue()` for file-mutating tools.
- **Constrained sampling (0.82.0):** `Tool.constrainedSampling` with strict JSON Schema `prefer` | `require`, plus OpenAI Lark/regex grammar variants. **This is the local-model reliability lever.**

Shell tools aren't a first-class concept — write a TS tool that shells out. Skills, by contrast, can carry arbitrary scripts.

## 5. MCP support

**Not in core.** Provided by extensions. Three+ competing implementations:

| Package | Approach |
|---|---|
| **`pi-mcp-adapter`** (<https://github.com/nicobailon/pi-mcp-adapter>) | **Token-efficient.** One proxy tool (~200 tokens) instead of registering N tools. Reads standard `.mcp.json`. Supports **stdio** (command+args), **HTTP** (StreamableHTTP with SSE fallback), **Unix sockets** via rmcp-mux, Bearer token + OAuth. Server lifecycle modes: `lazy` (default), `eager`, `keep-alive`, `lazy-keep-alive`. Caches tool metadata locally for search/discovery without live connection. `directTools` config promotes specific high-value tools to first-class pi tools. Motivating claim: *"A single MCP server can burn 10k+ tokens."* |
| **`@spences10/pi-mcp`** (<https://github.com/spences10/my-pi>) | stdio + HTTP servers configured via `mcp.json`, project-scoped, adds `/mcp` command. |
| `pi-mcp-extension`, `@qianhuan-lxs/pi-mcp-bridge` | Alternatives; bridge via dynamic context tools. |

**Per-agent filtering:** via `@tintinweb/pi-subagents` frontmatter `mcp:server-name` syntax (§3.1).

**For a 24GB rig with 98k–131k context, `pi-mcp-adapter`'s proxy-tool design is strictly better than Claude Code's MCP model** — dumping 26 tool schemas into a Qwen3.6 context is exactly the failure mode you want to avoid.

## 6. Hooks / lifecycle events / extensions

Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md>

Extensions are TypeScript modules exporting a default factory:

```typescript
export default function (pi: ExtensionAPI) {
  pi.on("event_name", async (event, ctx) => { ... });
  pi.registerTool({ ... });
  pi.registerCommand("name", { ... });
}
```

**Discovery:** `~/.pi/agent/extensions/` (global) or `.pi/extensions/` (project-local). **Hot-reload via `/reload`.**

### Event lifecycle (verified names)
- **Startup:** `project_trust` → `session_start` → `resources_discover`
- **Agent turn:** `before_agent_start` → `agent_start` → `turn_start` → `tool_call` / `tool_result` → `turn_end` → `agent_end`
- **Session control:** `session_before_switch`, `session_shutdown`, `session_compact`, `session_before_compact`, `session_before_tree`
- **Model:** `model_select`, `thinking_level_select`
- Also: `message_end` (used for normalizing provider errors, see §9.4)

Handlers can **block or modify tool calls**, inject context, customize compaction, and control user interaction — i.e. pi's event system is a superset of Claude Code's `PreToolUse`/`PostToolUse` hooks, and it runs **in-process in TypeScript** rather than shelling out to a script.

### Registration APIs
- `pi.registerTool()`, `pi.registerCommand()` (→ `/mycommand`), `pi.registerShortcut()`, `pi.registerProvider()` (0.81.0)
- `pi.appendEntry()` — persist state to the session (survives restarts)
- `pi.sendMessage()` — inject LLM-participatory context
- `pi.setActiveTools()` — dynamic tool activation

### ExtensionContext
`ctx.ui` (dialogs: `select`/`confirm`/`input`/`editor`; `notify`, `setStatus`, `setWidget`, `setTitle`; dialogs support `timeout` + `AbortSignal`), `ctx.sessionManager` (read-only session state, `getBranch()`), `ctx.modelRegistry`, `ctx.signal`, `ctx.cwd`, `ctx.getSystemPrompt()`, `ctx.isIdle()`, `ctx.shutdown()`, `ctx.mode`, `ctx.hasUI`, `ctx.isProjectTrusted()`.

**Command-only context:** `ctx.newSession()`, `ctx.fork(entryId)`, `ctx.switchSession(path)`, `ctx.waitForIdle()`, `ctx.reload()`.

**State best practice (verbatim from docs):**
```typescript
pi.on("session_start", async (_event, ctx) => {
  for (const entry of ctx.sessionManager.getBranch()) {
    if (entry.type === "message" && entry.message.toolName === "my_tool") {
      items = entry.message.details?.items ?? [];
    }
  }
});
```
Store mutable data in tool-result `details` so it branches correctly with the session tree.

**Security:** *"Extensions run with full system permissions; only install from trusted sources."*

## 7. Skills

Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md>

**Yes — pi implements the Agent Skills standard**, i.e. Anthropic-style `SKILL.md`.

- **Progressive disclosure confirmed:** skill *descriptions* stay in context at startup; the full `SKILL.md` loads only on demand.
- **Structure:** `SKILL.md` with frontmatter + instructions, plus optional scripts/references/assets.
- **Required frontmatter:** `name` (1–64 chars, lowercase alphanumeric + hyphens) and `description` (≤1024 chars).
- **Deviation from the standard:** *"Unlike the standard, Pi does not require this to match the parent directory."*
- **Sources:** global dirs, project folders, npm packages, settings config, CLI args.
- **Explicit invocation:** `/skill:name`, optionally with arguments.
- **Cross-compat:** <https://github.com/badlogic/pi-skills> — "Skills for pi coding agent (**compatible with Claude Code and Codex CLI**)". Your existing Claude Code skills should port.
- `@spences10/pi-skills` adds skill management/import/sync per-project.

**This is a genuine parity win** — pi's skills are directly interchangeable with Claude Code's.

## 9. Model / provider configuration

### 9.1 `models.json`
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/models.md>

Location: `~/.pi/agent/models.json`. **Reloaded on each `/model` visit** — you can edit it mid-session without restarting pi.

**Provider fields:** `baseUrl`, `api`, `apiKey` (optional), `headers`, `models[]`, `compat`, `modelOverrides`, `thinkingLevelMap`, `openRouterRouting`.
**Model fields:** `id` (**only required field**), `name`, `reasoning`, `input`, `contextWindow`, `maxTokens`, `cost`, `compat` (model-level override).

**`api` types (verified):**

| Value | Meaning |
|---|---|
| `openai-completions` | OpenAI Chat Completions — docs call it **"most compatible"**. Tool calls serialized as `tool_calls` on assistant messages + `role: "tool"` results. |
| `openai-responses` | OpenAI Responses API |
| `anthropic-messages` | Anthropic Messages API — `tool_use` / `tool_result` content blocks |
| `google-generative-ai` | Google Generative AI |
| `mistral-conversations` | Mistral SDK Conversations/Chat |
| (`bedrock` variants exist — see `BedrockCompat` in §9.3) |

**Value resolution for `apiKey` and `headers`** (three forms):
1. **Shell command:** `"!security find-generic-password -ws 'key'"` — executed at request time
2. **Env var:** `"$MY_API_KEY"` or `"${KEY_PREFIX}_${SUFFIX}"`
3. **Literal:** plain string
Escape `$` as `$$`; escape leading `!` as `$!`.

**Credential resolution order** (from `docs/providers.md`): CLI `--api-key` → `auth.json` → env var → custom keys in `models.json`.

**Built-in local providers:** `llama.cpp`, Ollama, LM Studio, vLLM.

### 9.3 Prompt caching
- `cacheControlFormat: "anthropic"` on OpenAI-completions providers.
- `supportsLongCacheRetention` across all api types.
- Cache hit rate visible in the TUI footer as **`CH`** (added 0.79.0).
- Community `pi-cache-optimizer` improves prompt/KV cache hit rates by keeping prompts stable — **relevant to llama.cpp KV-cache reuse**.

### 9.4 Context management / compaction
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md>

- **Auto-compaction triggers when** `contextTokens > contextWindow - reserveTokens`. Default `reserveTokens` = **16,384**.
- Cut point found by walking backwards until reaching `keepRecentTokens`, default **20,000**.
- Older messages are summarized; on subsequent compactions prior summaries are folded into the next pass.
- **Branch summarization:** navigating via `/tree` finds the common ancestor and summarizes the abandoned branch, injecting it as context.
- Both produce entries with: goal, constraints, progress, decisions, next steps, critical context; plus file tracking (read/modified) and LLM usage metrics.
- **Customization:** intercept `session_before_compact` and `session_before_tree`; `serializeConversation()` converts messages to text so you can summarize with a *different model*.
- Config in `settings.json` controls thresholds and auto-compaction on/off (manual `/compact` always available).

> **Rig-specific:** with `coder` at 131k context, defaults leave you compacting at ~115k. You can summarize with `utility` (Llama3.2-3B) via `session_before_compact` to avoid burning the big model on summarization. See §12.

**Context overflow recovery:** pi auto-detects overflow errors, compacts, and retries. If your provider's error text isn't recognized, `docs/custom-provider.md` says to normalize it in a `message_end` handler so it contains the phrase **`"context_length_exceeded"`**. — LiteLLM usually normalizes this already, but llama.cpp behind it may not.

### 9.5 Custom providers via extension
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/custom-provider.md>

```typescript
// override an existing provider's endpoint
pi.registerProvider("anthropic", { baseUrl: "https://proxy.example.com" });

// register a brand-new provider
pi.registerProvider("my-provider", {
  baseUrl: "https://api.example.com",
  apiKey: "$MY_API_KEY",
  api: "openai-completions",
  models: [{ id: "my-model", name: "My Model" }]
});
```
When `models` is supplied it **replaces all** existing models for that provider. `authHeader: true` sends `Authorization: Bearer`. `oauth` property enables browser/device-code flows with auto-refresh. `streamSimple()` for non-standard APIs. Test suites live in `packages/ai/test/`.

## 10. Local-model ergonomics

### 10.1 Built-in llama.cpp support
Source: <https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/llama-cpp.md>

pi integrates with **llama.cpp's router server** (multi-model):

```bash
llama-server --models-dir ~/models --no-models-autoload --jinja \
  --host 127.0.0.1 --port 8080 -ngl 999 -c 32768
```

- `--jinja` is **required** — it enables chat templates and tool calling.
- `--no-models-autoload` → explicit loading, router mode. **Omit `--model`/`-m`** or you get single-model mode.
- Auth: `/login llama.cpp`, or `LLAMA_BASE_URL` / `LLAMA_API_KEY` env vars. Default endpoint `http://127.0.0.1:8080`.
- `/llama` command loads/unloads models and downloads from Hugging Face with live progress (0.81.0). `/model` then selects it.
- Docs note: *"The router may be shared with other clients, so `/llama` always displays the router's current state."*
- Troubleshooting checks: `curl .../health`, `curl .../models`.

> ⚠️ Older writeups (e.g. <https://medium.com/@tolgaeren/running-pi-with-local-llms-c596aa14b062>) instruct `pi install npm:pi-llama-cpp`. As of 0.81.0+ llama.cpp management appears to be core/bundled (the CHANGELOG refers to "the llama.cpp extension" being fixed, so it may ship as a bundled extension). Exact packaging status: **likely bundled, unverified**.

**Relevance caveat for this rig:** the user runs **llama-swap** in front of llama.cpp, behind **LiteLLM**. pi's `/llama` router integration talks to llama.cpp's *own* router and will not see through LiteLLM. Use the generic OpenAI-completions path (§12) — `/llama` is not applicable here.

### 10.2 LiteLLM
**`pi-provider-litellm` v2.0.2** — <https://github.com/balcsida/pi-provider-litellm> · MIT · requires **pi ≥ 0.81.0**, Node ≥22.19.0.

```bash
pi install npm:pi-provider-litellm
export LITELLM_BASE_URL="https://litellm.your-domain.com"
export LITELLM_API_KEY="sk-..."
# or: /login litellm
```

- **Model discovery cascade:** `/model/info` (admin, rich metadata) → `/v1/models` on permission error → `/health` + per-endpoint checks for old proxies.
- Also supports LiteLLM MCP tools, Google ADC auth, Skills Gateway system-prompt injection, multiple provider aliases with separate credentials.
- Tunables: `LITELLM_DISCOVERY_TIMEOUT_MS`, `LITELLM_OFFLINE=1`.
- Credential priority: stored creds → env vars → a command that prints a fresh bearer token.

**Trade-off vs. hand-written `models.json`:** auto-discovery is convenient but it will **not** know your context windows or set the `compat` flags. Given the user already has a working hand-tuned `models.json` with the right compat flags, **the extension is optional and arguably a regression**. See §12/§13.

```json
          "reasoning": true,

}
```

**Flag-by-flag rationale** (each maps to a verified source comment in §9.2):
- `supportsDeveloperRole: false` — llama.cpp's shim only knows `system`. *(already in use, confirmed correct)*
- `supportsReasoningEffort: false` — llama.cpp rejects `reasoning_effort`. *(already in use, confirmed correct)*
- `supportsStore: false` — `store` is an OpenAI-platform field; harmless to disable, avoids a 400 if LiteLLM forwards it.
- `maxTokensField: "max_tokens"` — auto-detection can't infer this from a custom domain; llama.cpp wants the legacy field.
- `supportsStrictMode: false` — **default is `true`**. llama.cpp does not implement OpenAI's `strict` tool field. **Leaving this at default is a likely source of tool-call failures.** Start `false`, then see 12.3.
- `supportsOpenAIGrammarTools: false` — Lark/regex custom tools are OpenAI-specific; default is already false, set explicitly for clarity.
- `requiresToolResultName: true` — many llama.cpp-derived servers want `name` on tool results. If tool results come back malformed, toggle this first.
- `thinkingFormat: "qwen"` — Qwen models emit thinking in their own format. Alternatives worth trying if reasoning renders wrong: `"chat-template"` + `chatTemplateKwargs`, `"qwen-chat-template"`, or `"string-thinking"`.
- `cost: {input: 0, output: 0}` — makes pi's footer report real token counts without fake dollar amounts.

**`contextWindow` is the important addition.** Without it pi can't compute the auto-compaction trigger correctly (§9.4), and you'll either compact far too early or blow past the model's real limit.

### 12.2 `~/.pi/agent/settings.json` — compaction tuned for 131k
```json
{
  "provider": "homelab",
  "model": "coder",
  "autoCompaction": {
    "enabled": true,
    "reserveTokens": 24576,
    "keepRecentTokens": 32768
  },
  "defaultProjectTrust": "ask"
}
```
Bigger `reserveTokens` than the 16,384 default because local servers are less forgiving about overflow; bigger `keepRecentTokens` because Qwen3.6 needs more recent context to stay coherent than a frontier model does.

> ⚠️ Exact nesting of the auto-compaction keys is **likely, not verified** — `docs/settings.md` describes the capability ("Adjust auto-compaction behavior") without a verbatim schema dump. Confirm with `/settings` in the TUI before committing, and prefer setting it through `/settings` which writes the canonical shape.

### 12.3 Tool-call reliability escalation ladder
If `coder` produces malformed tool calls, work through this in order:

1. **Confirm `--jinja` is passed to every llama.cpp instance behind llama-swap.** Without it, tool calling is not wired up at all. *(verified requirement)*
2. Set `supportsStrictMode: false` (§12.1) — stops pi sending a `strict` field llama.cpp will choke on.
3. Toggle `requiresToolResultName` and `requiresAssistantAfterToolResult`.
4. **Try `supportsStrictMode: true`** — llama.cpp *does* support GBNF grammar-constrained decoding, and LiteLLM may map `strict` onto it. If it works, pi 0.82.0's `constrainedSampling: "require"` gives you schema-guaranteed tool arguments. **This is the highest-value experiment on this rig.** *(outcome unverified — must be tested)*
5. Fall back to `fast` (Qwen2.5-Coder-7B) for tool-heavy subagent work; it's a known-good tool caller.

## 13. Gaps vs Claude Code

| Gap | Severity on this rig | Mitigation |
|---|---|---|
| No built-in subagents | Medium | `@tintinweb/pi-subagents` is a genuine equivalent (parallel, worktrees, steering, per-agent model/tools). Costs you a trust decision on a third-party package. |
| No built-in MCP | Low | `pi-mcp-adapter` is arguably *better* — proxy-tool design saves ~10k tokens/server, which matters enormously at 131k. |
| No built-in LSP | **High** | This is the real gap. opencode feeds LSP diagnostics back on every edit, which is how you catch a 35B model hallucinating APIs cheaply. `@spences10/pi-lsp` / `pi-lens` close it but are unvendored. |
| No built-in permission system | Medium | `pi-sandbox` / `pi-defender`. Claude Code's allow/ask/deny is more mature. Matters more if you run unattended swarms. |
| No built-in plan mode / todos | Low | Extensions exist; also easily prompted. |
| Third-party dependency risk | **High** | Your swarm stack = 4 community packages from 4 different authors, each with full system access (docs warn explicitly). Core pi ships ~2–4 releases/week and can break them. |
| Smaller ecosystem/community | Low-Medium | 5,416 packages in the registry is not small, but quality varies wildly and there's no curation signal beyond download counts. |
| Docs thinner than Claude Code | Low | 31 doc files, generally good; some schemas (settings, agent frontmatter) aren't dumped verbatim. |

Ordered by value/effort. Confidence marked per item.

1. **Add `contextWindow` + `maxTokens` to every model in `models.json`.** *(verified)* Without these, auto-compaction math is wrong — pi can't know `coder` has 131k. Highest value, lowest effort.
2. **Add `supportsStrictMode: false` and `maxTokensField: "max_tokens"`.** *(verified flags; llama.cpp behavior likely)* `supportsStrictMode` **defaults to true** and is a probable cause of tool-call failures the user may currently be attributing to the model.
3. **Upgrade 0.82.x → 0.83.0.** *(verified)* Brings `pi auth print-api-key` / `print-bearer-token`, which is the clean way to hand credentials to spawned subagent processes without duplicating config.
